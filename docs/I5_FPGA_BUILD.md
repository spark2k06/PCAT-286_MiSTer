# I5 FPGA build and timing evidence

Date: 2026-09-10. Branch: `codex/spk286-xt-integration`. FPGA source commit:
`ab18fea`. Target: Cyclone V `5CSEBA6U23I7` (MiSTer).

## Reproduction

The complete command, including the timing-equivalence gate, Quartus build,
focused TimeQuest reports and bitstream hashes, is:

```sh
wsl bash -lc 'cd /mnt/d/GitHub/PCAT-286_MiSTer && bash scripts/build_i5_quartus.sh'
```

It uses the `raetro/quartus:mister` container unless `QUARTUS_IMAGE` overrides
it. The equivalent direct compilation command is:

```sh
wsl docker run --rm -v $(pwd):/build -w /build \
  raetro/quartus:mister quartus_sh --flow compile PCAT-286.qsf
```

Actual tool version: Quartus Prime 17.0.2 Build 602 Lite Edition. The complete
flow, fitter and assembler all completed with zero errors. The standard flow
took 33 minutes 32 seconds and the focused sign-off took a further 31 seconds
in the recorded container run.

## SPK286 timing fix and focused sign-off

The first successful fit exposed an SPK286 internal setup WNS of `-0.349 ns`
at 50 MHz. Its critical path crossed the combinational microcode ROM and then
an operand segment-limit comparison even while completing an already accepted
memory response.

The production operand variant factors that logically unrelated comparison out
of the pending-response path. It adds no storage or execution cycle. A direct
original-versus-variant bench checks every visible output, `blocked` and the
private `pending_q` state for five directed cycles plus 50,000 randomized
cycles. It passes 50,005 checks in both Icarus and Verilator.

The inherited reset stretcher changes on the falling edge. A one-stage local
SPK286 reset release now gives the high-fanout synchronous CPU reset a complete
clock period; it delays only reset release by one cycle and adds no running
wait state.

Final slow-100C focused TimeQuest results:

| Path group | Worst slack | Violated paths |
| --- | ---: | ---: |
| SPK286 internal setup, 50 MHz | `+0.171 ns` | 0 |
| SPK286 internal hold | `+0.262 ns` | 0 |
| SPK286 to XT bridge setup | `+9.418 ns` | 0 |
| XT bridge to SPK286 setup | `+12.138 ns` | 0 |
| Debug source-snapshot setup | `+5.664 ns` | 0 |
| Complete 50 MHz chipset clock setup | `+0.171 ns` | 0 |
| Complete 50 MHz chipset clock hold | `+0.244 ns` | 0 |

Thus the new CPU, bridge, debug capture and shared 50 MHz machine domain close
timing. The final instrumentation changes reduce the internal margin compared
with the previous fit, but it remains positive in the final slow-100C model.

## Global inherited timing boundary

The standard complete-machine TimeQuest summary still reports setup failure in
legacy framework/video/external-interface groups. At slow 100C the VGA group
is `-10.920 ns`, the x2 video group is `-5.099 ns`, the inherited virtual SDIO
group is `-1.087 ns`, and the HPS interface group is `-0.021 ns`. Global hold
passes at `+0.244 ns` and recovery passes at `+1.171 ns`.

These paths are outside SPK286 and its adapter, but they prevent claiming clean
whole-project timing sign-off. They are not new in kind: a nearby pre-integration
PCXT build report has four timing-failure corners, the same 256 dual-clock EGA
VRAM `mixed_port_feed_through_mode` critical warnings, and a worse video setup
WNS of `-28.136 ns`. That build is contextual evidence, not an exact controlled
resource comparison with the pinned import.

Accordingly, I5 has a reproducible successful compile, fit, assembler output,
RBF and passing timing for every new SPK286/bridge/50 MHz path. Its strict
whole-machine constraints acceptance remains qualified by the inherited video,
HPS and SDIO items above. No physical reliability claim is inferred from those
exceptions; I6 remains pending.
