### CPU: stack range to architectural control

At 100 C the representative path starts at `registers|gpr_q[69]` (SP bit 5)
and ends at the enable of `registers|ip_q[1]`. Its data delay is **23.248 ns**:
7.768 ns cell delay and 15.480 ns interconnect, with 21 logic levels and
-0.487 ns clock skew. Other endpoints include prefetch-count and micro-PC
registers; this is a shared control chain rather than IP arithmetic alone.

The fitted route includes:

```text
SP / call_gate_parameter_count_q
  -> Add26 / Add27 / LessThan39
  -> call_stack_range_fault / stack_range_fault
  -> service_segment / selected segment limit
  -> system_limit_fault / operand allowed
  -> task_gate_target_begin / descriptor_post_fault
  -> event selection / prefetch control
  -> IP enable
```

The cold CPU path starts at `call_gate_parameter_count_q[0]` and follows the
same range/fault family through `service_offset`, operand range/done and
event-gate validation, ending at IP enable. It has 18 levels and 22.655 ns
data delay. `service_segment[0]` has fanout 216 on the hot representative
path; `operand|allowed` and event selection also distribute control widely.

Relevant source: `spk286_micro_executor.sv`'s `call_stack_range_fault`,
`call_gate_frame_bytes`, `stack_request` and `system_limit_fault` equations;
`spk286.sv`'s `service_segment`, `service_offset`, segment selection and event
commit. The parameter-copy bound currently combines `SP + 2*N - 1` with
comparisons, then lets the resulting fault affect further selector logic.
The fitted Add names are synthesis labels, not an exact source-line mapping.

**Candidate:** first factor the small parameter-span/frame-size arithmetic
so the live 16-bit SP does not traverse two serial arithmetic operations.
Preserve 17-bit overflow/underflow behavior and the N=0 guard. Then consider
decoding the intended stack service before its fault qualification, checking
that selector changes cannot alter fault priority, error code or the point
of architectural commit. Changing the generated ROM or adding a CPU cycle
is not required by this first candidate.

Any CPU patch belongs in standalone SPK286 and must then be synced to PCAT.
Directed acceptance must cover parameter counts 0/1/31, stack limits and
wraparound, expand-down stacks, privilege-changing CALL/interrupt gates,
outer RETF/IRET, error frames, cancellation and fault restart. H07/H16's
atomicity and H15's descriptor-cache behavior are preservation obligations,
not evidence of a newly discovered functional bug in those stories.

### Keyboard: serial sequence construction

The cold worst path runs from the inferred event FIFO's
`PORT_B_WRITE_ENABLE_REG` through `portbdataout`, navigation-key decoding,
`index`, Add8..Add15 and `next_sequence` to `sequence_q[11]`.
It has 15 levels, **21.745 ns** data delay and **-2.554 ns** clock skew.
Cell delay is 14.310 ns and interconnect is 7.435 ns.

`spk286_at_keyboard.sv`'s `build_sequence` incrementally constructs a packed
sequence using a 32-bit integer index, conditional increments and variable
part-select writes. Unrolling the eight-byte loop creates a chain of adders
and steering logic. The FIFO launch type must also be inspected when
comparing a new fit; its name alone does not prove a write/read collision.

**Candidate:** construct the finite prefix/base/suffix combinations using
bounded byte counts and static concatenation or a shallow selector. Preserve
the current load edge and first-visible-byte timing. A registered decode
stage is a separate option if an extra keyboard latency is explicitly
accepted; it is not necessary for the first combinational candidate.

Directed acceptance: exhaustive combinational old/new sequence equality for
code, pressed/extended, translation, Num Lock and both Shift states; the
existing keyboard FIFO test for empty/full and simultaneous enqueue/dequeue;
Pause, Print Screen and all navigation make/break sequences. This is the
first recommended RTL experiment because it is small and independent of
CPU protected-mode semantics.

### SDRAM owner and bridge: upstream acceptance depth

The hot owner path starts at `missing_ega_sync[1]`, through machine reset,
BIU/width and address decode, code-buffer bypass, data-buffer bypass,
`request_accept`, and KFSDRAM's address-selection logic, ending at
`u_KFSDRAM|sdram_address[8]`. It has 18 levels and **23.457 ns** data delay.
The physical output violation shares this upstream chain and ends at
`SDRAM_A[12]`, where the owner places UDQM during a READ/WRITE command.

These are real same-domain request/control paths. The source's reset-related
name does not justify excluding downstream address or acceptance logic.
Likewise, the CPU-to-bridge violation traverses `shutdown -> cpu_core_reset`
(fanout 1097), width/address decode, device acceptance and bridge state.

**Candidate:** capture a normalized physical request at the owner boundary
and launch KFSDRAM from that stable record, or factor acceptance and byte
mask decoding before this boundary. Preserve one outstanding transaction,
accepted-transfer draining on cancellation, CPU/DMA/HPS ordering, writes,
refresh and four-word instruction fills. A launch register can add one
cycle to misses/writes, so benchmark its cost separately; don't remove real
READY dependencies. The local controller already has positive internal
margin, so replacing it wholesale is not the first experiment.

## Verified CDC constraint correction

Before the correction, the worst global setup path was a 50 MHz reset/ROM
hold source to `prebios_video_sync1_q`, clocked by the video PLL. The video
adapter already has the dedicated two-stage scalar chain and consumes only
`prebios_video_sync2_q`. `SYSTEM.sdc` constrained analogous first-stage
crossings but omitted this one.

The only production change adds:

```tcl
at_sync prebios_video [at_clock FPGA_CLK2_50] {*u_video|prebios_video_sync1_q}
```

The source is the system clock even with the optional CPU divider. This
exception targets only asynchronous arrival at the **first** register;
stage-one-to-stage-two remains a normal video-clock path. There is no
whole-domain cut, multicycle relaxation, frequency reduction or change
to external SDRAM delays.

For every common non-global/non-video group, the A/B checker compared its

The corrected report extracted one actual path between the two stages in

A repeat with the final frozen tools reproduced every corrected group's

the receipt retains these differences. Their row ordering is not an invariant.

## SDRAM photo and external budget

The user supplied [this module photo](../evidence/timing-50mhz-20261001/sdram-module.jpg).
It shows Winbond branding and a W9825-family marking; the wire obscures part
of the reference. W9825G6KH/JH and the exact speed grade cannot be certified
from the photo. The complete module capacity/revision, routing and board
skew also remain unconfirmed.

Conditional reference only: Winbond's
[W9825G6KH A05 datasheet](https://docs.rs-online.com/eb6b/0900766b817040a8.pdf),
§9.5, gives CL2 tAC max 6 ns, tOH min 3 ns, input setup 1.5 ns and input
hold 0.8 or 1.0 ns depending on grade. Its tRCD/tRP vary from 15 to 20 ns.
KFSDRAM currently selects CL2. These values do not identify the actual part
or validate the physical module.

The inherited SDC uses input max/min 6/3 ns and output max/min 2/+1.5 ns.
The input values resemble chip-only access/hold numbers and have no documented
PCB flight-time allowance. A positive output-min value must not be assumed
to model the chip's positive hold requirement: with zero board skew, the
usual hold budget is negative. A complete source-synchronous budget needs
clock/data flight-time bounds, loading/rise-time corrections and the actual
port-reference convention. Confirm those before changing signs or phases.
Therefore the current positive SDRAM hold slacks are **not** external sign-off.
